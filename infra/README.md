## Staging at a glance

| Piece | Where | Defined in |
|---|---|---|
| API (NestJS, Docker) | Render web service `flowtop-api-staging`, Singapore, `starter` | [render.yaml](render.yaml), [backend/Dockerfile](../backend/Dockerfile) |
| Database (Postgres 17) | Render Postgres `flowtop-staging-db`, Singapore, `basic-256mb`, no outside access | [render.yaml](render.yaml) |
| Public bucket: product photos, marketing media | Cloudflare R2 `flowtop-staging-public`, public read | Set up by hand, below |
| Private bucket: customer documents | Cloudflare R2 `flowtop-staging-private`, never public, 15-minute signed links only | Set up by hand, below |

**Secrets live only in Render's environment settings**, never in the repo, never in a log line. The repo holds names and placeholders; the values are entered in the dashboards below. CI blocks any `.env` file and scans every commit for credentials.

## One-time setup

Do these in order. About 30 minutes.

### 1. Cloudflare R2: the two buckets

1. Cloudflare dashboard → **R2** → **Create bucket**, twice:
   - `flowtop-staging-public`, location hint **Asia-Pacific**
   - `flowtop-staging-private`, location hint **Asia-Pacific**
2. **Public bucket only:** Settings → **Public access** → connect a custom domain such as `media-staging.<your domain>`. The `r2.dev` address works for a quick test but is rate-limited, so do not leave staging on it. That URL becomes `MEDIA_PUBLIC_BASE_URL`.
3. **Private bucket:** leave public access **off**. Check it says "Not allowed". The API never makes a public link to it; it only hands out signed links that expire after 15 minutes.
4. R2 → **Manage API tokens** → **Create API token**: permission **Object Read & Write**, applied to **those two buckets only**. Copy the Access Key ID and Secret Access Key now, because Cloudflare shows the secret once.
5. Note your **Account ID** (R2 overview page). The endpoint is `https://<account id>.r2.cloudflarestorage.com`.

### 2. Render: the API and the database

1. Render dashboard → **New** → **Blueprint** → connect the GitHub repo `Siddharth-k7/FlowTop`.
2. Set **Blueprint path** to `infra/render.yaml`.
3. Render asks for every value marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `CORS_ORIGINS` | The staging admin and public site URLs, comma-separated |
   | `ADMIN_URL` | The staging admin URL |
   | `MEDIA_PUBLIC_BASE_URL` | The public bucket URL from step 1.2 |
   | `S3_ENDPOINT` | `https://<account id>.r2.cloudflarestorage.com` |
   | `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | The R2 token from step 1.4 |

   `MFA_ENCRYPTION_KEY` is generated by Render. **Never change it**: every stored MFA secret would become unreadable.
4. **Apply**. Render creates the database, builds `backend/Dockerfile`, and starts the API. On start the container runs `prisma migrate deploy`, which applies any migrations not applied yet, then starts the server.

### 3. Seed the database

Render dashboard → `flowtop-api-staging` → **Shell**:

```sh
read -rs SEED_ADMIN_PASSWORD && export SEED_ADMIN_PASSWORD   # type it; nothing is shown or saved
SEED_ADMIN_EMAIL=you@flowtop.in node dist/database/seed.cli.js
```

This writes the permissions, the three roles and the eight settings, and creates your super admin. It is safe to run again; it never overwrites an existing user or a changed setting. Then log in and turn on MFA straight away (`POST /api/v1/auth/mfa/setup`).

### 4. Confirm it is up

```sh
curl https://flowtop-api-staging.onrender.com/health
# {"data":{"status":"ok","database":"up"}}
```

Use the URL Render shows if it differs. **Staging is not done until this answers with `"database":"up"`.**

### 5. Lock the pipeline

Ask a repo admin to make these required checks on `main`: **Secret scan (gitleaks)**, **Backend**, **Backend image**, **Frontend**, **Admin**, **UI kit**. Render only deploys a commit once all of them pass (`autoDeployTrigger: checksPass`).

## Deploying

**Normally you do nothing.** Merge to `main` → CI runs → once every check passes, Render builds and deploys. Only changes under `backend/` trigger an API deploy.

During a deploy Render starts the new container, waits for `/health` to answer, then moves traffic over. If migrations or start-up fail, the health check never passes and the old version keeps serving.

**Deploy by hand:** Render → `flowtop-api-staging` → **Manual Deploy** → **Deploy latest commit**.

**Migrations:** the container runs `prisma migrate deploy` on start. It applies only committed migrations, never resets, and holds a lock so two containers cannot run them at once. CI fails any PR whose schema and migrations disagree.

## Rolling back

1. Render → `flowtop-api-staging` → **Events**.
2. Find the last good deploy → **Rollback**. Render redeploys that exact image.
3. Rolling back turns auto-deploy off. Turn it back on (Settings → Auto-Deploy) once a fix is on `main`.

**A rollback does not undo database migrations.** The older code runs against the newer schema, so:

- Write migrations that the previous release can live with: add a column before using it, and stop using a column before dropping it, in separate releases.
- To undo a migration, write a new migration that reverses it and deploy forward. Never edit or delete a migration that has been applied.

Database restore from backup is covered in `infra/RESTORE.md` (task 5.2).

## Where logs live

| What | Where |
|---|---|
| API logs: requests, errors, the start-up and migration output | Render → `flowtop-api-staging` → **Logs** (live tail and search) |
| Deploys: builds, health checks, rollbacks | Render → `flowtop-api-staging` → **Events** |
| Database: connections, slow queries, disk | Render → `flowtop-staging-db` → **Metrics** and **Logs** |
| Buckets: storage used, requests | Cloudflare → **R2** → bucket → **Metrics** |
| CI runs | GitHub → **Actions** |

How long Render keeps logs depends on the workspace plan. For longer retention and alerting, add a log stream to an external provider (task 5.3).

The API never logs a secret. The staging rehearsal below checks this by searching the full container log for every secret it used.

## Secrets: where each lives

| Secret | Lives in | Rotating it |
|---|---|---|
| `DATABASE_URL` | Managed by Render, linked from the database | Render rotates it with the database credentials |
| `MFA_ENCRYPTION_KEY` | Render environment (generated) | **Do not.** It would need a migration that re-encrypts every MFA secret |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Render environment | Create a new R2 token, update both in Render, redeploy, then delete the old token |
| Super admin password | Nobody's file: typed once into the seed | Use password reset |

## Rehearse staging locally

Before changing the image or the deploy, run the production image against a local Postgres and S3-compatible store:

```sh
docker build -t flowtop-api backend
docker run --rm -p 4000:4000 --env-file <a file with the staging variables, kept out of the repo> flowtop-api
curl http://localhost:4000/health
```

CI also rebuilds the image on every PR (the **Backend image** check), so a broken Dockerfile never reaches Render.
